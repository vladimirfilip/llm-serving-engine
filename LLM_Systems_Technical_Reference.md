## 1. CUDA fundamentals, quickly

A kernel launch spawns a grid of thread blocks, each holding up to 1024 threads. Blocks get scheduled onto the GPU's streaming multiprocessors (SMs), and within an SM, threads execute in fixed groups of 32 called warps: this is the real unit of execution, not the individual thread. Every thread in a warp runs the same instruction on the same clock cycle, differing only in which data it touches (SIMT, single instruction multiple threads). If threads in a warp take different branches of an `if`, the hardware doesn't run them in parallel: it runs both paths serially, masking off whichever threads don't apply to each path, so a divergent branch costs roughly the sum of both paths rather than the max of them. That's why kernels are written to keep control flow uniform across a warp wherever the algorithm allows it.

Memory sits in a hierarchy with a steep speed gradient. Registers are private to a thread and fastest. Shared memory (SRAM) is on-chip, shared by every thread in a block, and programmer-managed: you explicitly copy data into it and read it back out, and it's an order of magnitude faster and lower-latency than the alternative, global memory (HBM), which sits off-chip, is shared by the whole GPU, and is by far the largest tier but also the slowest. That gap is the reason every optimization in this document, kernel fusion, FlashAttention's tiling, comes down to the same move: keep data on-chip as long as possible and minimize round trips to HBM. It's also the mechanism behind latency hiding. An SM can hold many resident warps at once, and when one warp issues a slow HBM load and has to wait, the SM switches to a different resident warp that has work ready, so the wait gets hidden behind other warps' progress instead of stalling the SM outright. This is the actual reason occupancy matters (section 3): more resident warps means more options to switch to while any given warp is stuck waiting on memory.

Global memory is serviced most efficiently when a warp's 32 threads touch a contiguous, aligned chunk of memory, since the hardware can combine that into one wide transaction (coalescing). Scattered or strided access patterns force multiple separate transactions to service a single warp's request, burning bandwidth on data that gets fetched but never used. This is the global-memory version of the bank-conflict problem shared memory has (section 3 covers that specifically); both come down to the same underlying rule, that the hardware rewards uniform, contiguous access across a warp and punishes scattered access.

## 2. Transformers from the ground up

A language model predicts a probability distribution over the next token given the tokens so far, and generates text by repeatedly predicting one token, appending it, and repeating: autoregressive generation. Text is first tokenized into subword units, and each token is mapped to a vector via a learned embedding table lookup, giving a sequence of vectors, one per position. That sequence, called the residual stream or hidden states, is what actually flows through the network. Each layer computes some update and adds it back into the stream (`x = x + LayerOutput(x)`, a residual or skip connection) rather than replacing the stream outright, which is what makes very deep networks trainable: even if a given layer's contribution starts out close to zero, the stream still passes through undisturbed. At the end, after one final normalization, a linear projection maps the last position's vector to one score, a logit, per vocabulary entry, and softmax turns those scores into a probability distribution over the next token.

Attention is the mechanism that lets a position's vector get updated based on other positions' content, and it's worth deriving properly since everything past this section assumes it. Each position's vector passes through three separate learned linear projections, producing a query, a key, and a value vector: `Q = xW_q`, `K = xW_k`, `V = xW_v`. Read the query as "what this position is looking for" and the key as "what this position offers, if matched against." For a given query position, take its dot product against every key vector; a large dot product means the query and that key point in a similar direction, a strong match. Collect all of one query's dot products against every key into a row of raw scores, `QKᵀ`, divide by `√d` (`d` the dimension of each Q/K vector, see below for why), and run softmax across that row so the scores become a probability distribution summing to 1, the attention weights. The output at that position is the weighted sum of every position's **value** vector, weighted by those probabilities: positions the query attends to strongly contribute most of their value vector to the result. In one line, `Attention(Q,K,V) = softmax(QKᵀ/√d) V`, exactly the S / P / O notation the FlashAttention section (section 4) builds on directly.

The `√d` divisor isn't cosmetic, and it's worth understanding why rather than taking it on faith. As dimension `d` grows, the dot product of two vectors with roughly unit-variance components grows in expected magnitude too, simply because you're summing more terms. Left unscaled, pre-softmax scores would grow with `d`, pushing softmax into a sharply peaked, saturated regime (one weight near 1, the rest near 0) regardless of how meaningfully different the underlying matches actually are, which flattens gradients during training. Dividing by `√d` keeps scores in a range where softmax stays well-behaved no matter how large the head dimension gets.

Multi-head attention runs this whole mechanism several times in parallel instead of once. Split the model dimension into `H` heads, each with its own, smaller Q/K/V projections of dimension `d/H`; run attention independently within each head, concatenate the H outputs back together, and apply one more linear projection to mix them. Different heads are free to specialize in different kinds of relationships between positions, since each head's weights are learned independently.

A decoder-only model like Llama or GPT generates text left to right, so a position must never be allowed to attend to positions after it: at generation time later tokens don't exist yet, and training has to respect that same constraint or the model learns to cheat by looking ahead. This is enforced with a causal mask: before the softmax, every score for a query position `i` and key position `j` with `j > i` is set to negative infinity, so it becomes exactly zero after softmax. This masking is also what makes a KV cache a coherent idea in the first place. Because position `i` only ever attends to positions `≤ i`, and a position's own key and value vectors depend only on that position's input and never on anything later, a position's K and V never change once computed. They can be computed once and reused at every later step instead of recomputed, which is the entire mechanic behind caching K and V (section 6 works out the memory and bandwidth consequences of this in full).

After attention mixes information across positions, each position independently passes through a small feed-forward network, typically two or three linear layers with a nonlinearity between them, applied identically to every position with zero cross-position interaction: this is where most of the model's per-token computation happens, complementing attention's job of moving information between positions. A normalization step (the classic choice is LayerNorm; section 6 covers Llama's RMSNorm variant) wraps each of the attention and FFN sublayers to keep activations well-scaled as they pass through many stacked layers, commonly dozens in a modern model. Generating text with this architecture happens in two distinct phases. Prefill runs the whole input prompt through the model in a single pass, computing every position's K and V and producing a prediction for the token right after the prompt. Decode then repeats a one-token-at-a-time loop: take the single newest token, run it through the model, computing only its own K, Q, V and reusing every earlier position's cached K,V per the masking argument above, get the next token, append it, and go again. That prefill/decode split, and the fact that decode only ever adds one new position's worth of K,V per step, is the foundation the rest of this document builds on.

**One decode step, made concrete.** Putting the pieces above together: say `n-1` positions are already cached, and a new token's embedding `x` has just arrived at layer 1. The same shape repeats with each layer's own weights, `L` times total (section 6 gives Llama's specific `L`; everything else below is left generic on purpose).

Inside each layer: `x_norm = Norm(x)`. Project only the new position, `Q = x_norm W_q`, `K = x_norm W_k`, `V = x_norm W_v`, each split into `H` heads. Inject position information into `Q` and `K` however this particular model does that (section 2 doesn't specify a mechanism; section 6 covers Llama's, RoPE). Append this layer's new `K`, `V` into this layer's own cache, which now covers positions 1 through `n`. For each head, `scores = Q · Kᵀ/√d` against every cached position, no masking needed here since decode's cache never holds a future position to begin with, masking is what prefill needs, since it scores every position at once. Then `weights = softmax(scores)`, `head_out = weights V`, concatenate the heads and project back down, `attn_out = concat(heads) W_o`, and add it back into the stream: `x = x + attn_out`. Norm again, `x_norm = Norm(x)`, run the feed-forward network, and add that back too: `x = x + FFN(x_norm)`. That `x` is what layer `l+1` receives.

After the last layer: one more `Norm`, then the linear projection and softmax from the opening paragraph above, now with that final norm made explicit. Whatever comes out is the distribution over the next token; picking an actual token from it, greedy, top-p, whatever sampling scheme, is a separate step outside the network entirely.

## 3. Kernel fusion, occupancy, and profiling with ncu

Fusion helps because elementwise and normalization ops are memory-bound, not compute-bound. RMSNorm, a residual add, an activation function: each does O(1) FLOPs per element but has to round-trip that element through HBM. Two unfused kernels means kernel A reads X from HBM, computes, writes Y back to HBM; kernel B reads Y back, computes, writes Z. Fusing them means reading X once, holding the intermediate in registers or shared memory, writing Z once. You've eliminated a full HBM write and read of the intermediate tensor. For N fused ops the savings scale with the number of eliminated round trips, which is why a fused RMSNorm-plus-residual kernel is worth writing by hand rather than trusting the framework's op-by-op execution.

Occupancy is the ratio of resident warps to the SM's maximum, and it's capped by whichever resource runs out first: registers or shared memory. On an A100 SM, that's 65,536 32-bit registers and 192 KB of combined L1/shared memory, supporting up to 2,048 resident threads. If your kernel uses 64 registers per thread, you can fit at most 65536/64 = 1024 threads' worth of registers, half the SM's thread capacity, before register pressure caps you below full occupancy. Shared memory works the same way: a kernel that claims 48 KB of shared memory per block limits you to 4 concurrent blocks on that SM regardless of thread count. `nvcc --ptxas-options=-v` reports register usage per kernel; ncu reports the achieved number directly.

One correction worth internalizing: occupancy is not the goal, it's a means of hiding memory latency behind other warps' independent work. A kernel at 100% occupancy that's still bandwidth-bound gains nothing further from occupancy, and a kernel with enough independent work per thread (more registers holding more in-flight values) can outperform a higher-occupancy version of itself with less work per thread. Treat occupancy as a diagnostic, not a target.

Bank conflicts: shared memory is banked, 32 banks, 4 bytes wide each, and a thread's word maps to bank `(address / 4) % 32`. A warp accessing 32 consecutive floats hits all 32 banks once each, no conflict. A warp accessing shared memory with stride 32 floats (a common pattern when reading down a column of a tiled matrix stored row-major) has every thread land on the same bank, serializing what should be a single-cycle access into 32. The standard fix is padding: allocate the shared-memory array one element wider than the tile size, which shifts the stride off the 32-alignment and breaks the conflict. ncu's `l1tex__data_bank_conflicts` metrics will show this directly if you're unsure whether you have one.

Warp shuffle intrinsics (`__shfl_down_sync`, `__shfl_xor_sync`) exchange register values between lanes in a warp without touching shared memory at all, which matters for the inner loop of a reduction or a softmax's row-max/row-sum: a tree reduction across 32 lanes takes log2(32) = 5 shuffle steps with zero shared-memory traffic and no `__syncthreads()` barrier, versus a shared-memory-based reduction that needs the barrier at every level. Use shuffles for intra-warp reductions and fall back to shared memory only for the inter-warp combination step.

On ncu specifically: it profiles one kernel launch at a time and gives you three things that matter for deciding what to fix next. Achieved occupancy versus theoretical, and which resource (registers, shared memory, block size) is the limiter. Memory throughput as a percentage of the device's peak HBM bandwidth, which tells you where you sit on the roofline (section 9). And a warp stall-reason breakdown, which is the part that actually tells you what to do: `stall_long_scoreboard` means warps are waiting on a global memory load, so you're bandwidth-bound or your access pattern isn't coalescing; `stall_barrier` means warps are waiting at a `__syncthreads()`, usually from divergent control flow or unbalanced work across threads in a block; `stall_short_scoreboard` means warps are waiting on shared memory or the MIO pipe, which is your signal to go check for bank conflicts. Knowing these three stall reasons by name, and what each implies about what to change, is the difference between having run ncu and having gotten anything out of it.

## 4. FlashAttention-2

Standard attention computes S = QKᵀ/√d (an N×N matrix), P = softmax(S) row-wise, then O = PV. This looks compute-heavy (O(N²d) FLOPs), but naive implementations write S to HBM, read it back for the softmax, write P, and read P back for the final matmul: multiple full N×N round trips through HBM. That HBM traffic dominates the wall-clock at any interesting sequence length, so despite the FLOP count, naive attention is firmly memory-bandwidth-bound rather than compute-bound.

FlashAttention's fix is to never materialize the full N×N matrix. Tile Q, K, and V into blocks that fit in SRAM (shared memory), and compute the output incrementally using a running, or "online," softmax as you sweep across K/V blocks for a given Q block. You need only O(block²) working memory and O(N) output memory, and each element of Q, K, V is touched by HBM close to once rather than several times.

The online softmax (Milakov and Gimelshin, 2018, reused directly by FlashAttention) is the part worth understanding precisely, because it's exact, not an approximation, and that surprises people. Track a running max `m` and running unnormalized sum `l` alongside a running output accumulator. When a new K/V block arrives, compute its local max, take the new global max as `max(m_old, m_local)`, and rescale the OLD accumulated sum and output by `exp(m_old - m_new)`. That rescale factor exactly undoes the previous max-subtraction so it can be redone consistently against the new, larger max. Add in the new block's contribution (itself scaled by `exp(m_local - m_new)`), and move to the next block. Divide by the running sum at the end. Because every rescale is an exact algebraic correction rather than a heuristic, the result is bit-for-bit the same numerically-stable softmax you'd get from the standard two-pass algorithm. Nothing is approximated; only the order of operations changes.

FlashAttention-1 (Dao et al., 2022) reaches only 25 to 40% of a GPU's theoretical peak FLOPs/s despite this, and the paper is specific about why: suboptimal work partitioning between warps. Within a thread block, FA1 splits K and V across warps ("split-K"): each warp computes a partial `QKᵀ·V` slice, and all warps then have to write their partial results to shared memory, synchronize, and sum them. That's real communication cost paid on every tile.

FlashAttention-2 (Dao, 2023) fixes this with three specific changes, and gets roughly 2x over FA1, reaching 50 to 73% of peak on A100. First, it reduces non-matmul FLOPs (the rescaling and bookkeeping arithmetic, which runs on CUDA cores rather than tensor cores and is disproportionately slow relative to the matmuls it sits next to). Second, it parallelizes across the sequence-length dimension as well as batch and heads, launching more thread blocks so occupancy stays high even when batch×heads is small but sequences are long, exactly the shape of long-context, small-batch inference. Third, and this is the detail worth being able to draw on a whiteboard: within a thread block, FA2 splits **Q** across warps instead of K/V, keeping K and V visible to all warps. Each warp now owns its own Q slice, computes its own slice of `QKᵀ` against the full, shared K/V tile, and produces its own output slice directly, with zero inter-warp communication and no shared-memory round trip needed to combine results. FA2 was also rewritten on top of Nvidia's CUTLASS 3.x and CuTe primitives rather than hand-rolled CUDA, which is itself a signal: getting close to peak GEMM efficiency on modern GPUs increasingly requires a template library built for exactly this, not vanilla CUDA C.

One nuance that matters directly for a decode-heavy serving engine: FA2's sequence-parallelism fix targets prefill, where you have many query rows to split across. Decode has exactly one new query row attending to N cached K/V rows, the limiting case of that same shape, and with only one query row there's nothing left to split across Q blocks, so a naive FA2-style kernel can leave the GPU under-occupied during decode. The standard answer is to split along the **KV** dimension instead for decode (the FlashDecoding-style approach used by most production serving kernels): partition the cached K,V across multiple thread blocks, have each compute a partial output over its slice using the same online-softmax bookkeeping, then run one cheap final reduction across the partial results. "FlashAttention-2" as usually described is a prefill-shaped algorithm; the decode step of a serving engine needs this KV-split variant, and it's worth knowing that distinction cold since it's an easy thing to gloss over.

## 5. Triton

Triton is a Python-embedded language and compiler, originating at OpenAI, for writing GPU kernels at block granularity instead of per-thread. A `@triton.jit` function operates on a tile of data at a time: `tl.load` a block (with a `mask` argument handling out-of-bounds reads at sequence boundaries), do the arithmetic, `tl.store` the result. The compiler works out the thread-to-data mapping, vectorization, coalescing, and much of the shared-memory scheduling on its own, then lowers through LLVM to PTX. Tunables like `num_warps` and `num_stages` (software-pipelining depth, how many loop iterations' worth of loads get issued ahead of the compute that consumes them, to hide latency) can be swept automatically with `triton.autotune`.

The honest tradeoff: Triton gets you most of hand-tuned CUDA's performance, often 80 to 90%-plus on fusion-heavy elementwise, reduction, and attention-shaped kernels, for a fraction of the development time, because the compiler absorbs coalescing and scheduling work you'd otherwise hand-roll. What it doesn't expose is fine control: explicit bank-conflict-avoidance patterns, precise register allocation, and warp-specialization tricks like FA2's own Q-split partitioning, since Triton's block abstraction doesn't give you per-warp control the way raw CUDA does. That's exactly why production engines like vLLM and TensorRT-LLM hand-write the hottest kernels (attention, the core GEMMs) in CUDA and CUTLASS while leaning on Triton for everything else and for fast iteration. It's also the reasoning behind pairing a hand-written CUDA kernel with a Triton FlashAttention-2 implementation in the same project: one proves you can go all the way down when it matters, the other proves you know when not to.

## 6. Llama's architecture, and why decode is memory-bound

Four deviations from the original Transformer, each chosen deliberately, plus the KV-cache mechanic that determines everything about how you'd serve the model efficiently.

**RMSNorm.** LayerNorm computes `(x - mean(x))/std(x) * gamma + beta`. RMSNorm drops the mean-centering and the bias, keeping only `x / sqrt(mean(x²) + eps) * gamma`. The empirical case (Zhang and Sennrich) is that recentering contributes little to LayerNorm's benefit, so cutting it saves a full reduction pass (computing the mean) at essentially no quality cost. This is precisely what a fused RMSNorm kernel fuses: the RMS reduction, the elementwise scale, and, in a pre-norm block, the following residual add, into one pass over the tensor instead of three.

**Pre-normalization.** The norm sits on the input to each attention or FFN sublayer, `x + Sublayer(Norm(x))`, rather than on its output, `Norm(x + Sublayer(x))` as in the original Transformer. The residual stream itself stays unnormalized end to end, giving gradients a direct path back to any layer without passing through a normalization at every step, which is what lets very deep transformers train stably without post-norm's aggressive learning-rate warmup requirement.

**RoPE.** Rather than adding a position vector, RoPE rotates pairs of dimensions in Q and K by an angle that depends on position. Split the head dimension into pairs; for pair `i` at position `m`, rotate by `θ_{m,i} = m · base^(-2i/d)` (Llama 2 uses base 10000; Llama 3 raises it to 500000, more below). The property that makes this worth the complexity: rotation is an isometry, so the dot product between a rotated query at position `m` and a rotated key at position `n` depends only on the rotation of their difference, i.e. only on `(m - n)`, not on `m` and `n` individually. Relative positional encoding falls out of an operation that looks purely absolute. This is also the mechanism behind context extension: techniques like NTK-aware scaling rescale the `θ_i` frequencies so the same rotation range that used to span positions [0, 8192] now spans [0, 131072]. Raising the base from 10000 to 500000, which is exactly what Llama 3 did to extend from an 8192-token training context to 131072, lowers the rotation frequency across every dimension pair; it isn't an arbitrary hyperparameter bump, it's the direct lever for how far the rotation "unwinds" before it starts aliasing.

**GQA.** Standard multi-head attention gives every query head its own K/V head. Llama 3 fixes 8 KV heads and shares them across query heads: 32 query heads in the 8B model (4:1), 64 in the 70B (8:1), 128 in the 405B (16:1), a ratio that grows with model size since larger models tolerate more compression per head and the memory savings matter more at scale. This is not a detail to gloss over for a serving engine, because KV cache size scales with the number of **KV** heads, not query heads: going from MHA to 8-way GQA on the 70B model is an 8x reduction in KV cache memory for identical sequence length and batch size, for under 0.5% quality cost on standard benchmarks. Concretely, KV cache bytes per token per layer = `2 (K and V) × n_kv_heads × head_dim × bytes_per_element`. That's the number that determines how many concurrent sequences fit in a fixed amount of GPU memory, and it's exactly what a paged KV-cache block allocator has to get right: block size in bytes must be computed off `n_kv_heads`, not query-head count, or the memory accounting is wrong by the GQA ratio.

**SwiGLU.** The FFN is `(SiLU(xW1) ⊙ xW3) W2`: two parallel up-projections, one gated through a SiLU activation, multiplied elementwise, then projected back down. The detail worth knowing cold: this adds a third weight matrix versus a plain ReLU FFN, so at matched parameter count the hidden dimension shrinks, roughly to two-thirds of what a standard 4x-expansion ReLU FFN's hidden dim would be, to keep total parameters comparable. If you see a config with an FFN dimension that doesn't look like a clean 4x multiple of the model dimension, this is why.

**KV caching, and the insight that explains the rest of this document.** Without caching, generating token N+1 means recomputing K and V for every one of the N previous tokens from scratch, every single decode step: O(N) redone work at each of N steps. Caching K and V per layer, per past token, changes each decode step to: project Q, K, V for only the new token, append the new K,V to the cache, then attend that one query against the full cached K,V. Per-step compute becomes O(1) new projection work plus attention against a cache that's mostly being **read**, not recomputed.

Here's the payoff: at batch size 1, a decode step reads the model's entire weights (and the growing KV cache) from HBM to produce a comparatively tiny amount of new arithmetic per byte read. Arithmetic intensity is low, so a single-sequence decode step is firmly bandwidth-bound, and the tensor cores sit mostly idle waiting on HBM. Batch multiple sequences' decode steps together, though, and you read the **same** weights once while multiplying them against B different sequences' activations, amortizing the fixed cost of streaming weights from HBM over B units of useful work. Arithmetic intensity rises roughly with batch size (the KV-cache read doesn't get shared this way, since it's per-sequence, but the dominant weight-read cost does). This single fact is why continuous batching, chunked prefill, and weight-only quantization all exist: every one of them is, underneath, a way to either raise effective batch size or cut the bytes streamed per step, because decode's bottleneck is bytes moved from HBM, not FLOPs computed.

## 7. Continuous batching and PagedAttention

Static batching waits for B requests, then runs every decode step for the whole batch until the longest sequence in it finishes, padding the shorter ones to match. A short request sharing a batch with a long one is blocked behind it for the batch's entire remaining lifetime: literal head-of-line blocking, plus wasted GPU cycles computing over pad tokens that contribute nothing.

Orca (Yu et al., OSDI 2022) fixed this by batching at the **iteration** level instead of the request level. After every single decode step, any sequence that just hit EOS or its length cap is evicted immediately, and a waiting request can be admitted into the freed slot on the very next step, without waiting for anyone else in the batch. The batch is a dynamically managed set rewritten every step, not a fixed unit created once and torn down together. This only works cleanly with a KV-cache allocation strategy that can grow and shrink per sequence without needing contiguous memory reserved up front, which is exactly what PagedAttention provides, and the two are typically shipped together (vLLM does both).

One refinement worth knowing by name: naively dropping a new request's prefill into the same iteration as a batch of ongoing decodes is a problem because prefill is compute-bound (it processes the whole prompt in parallel, saturating the GPU) while decode is memory-bound (one token per sequence at a time). A long prefill sharing an iteration with decodes spikes that iteration's latency for every sequence currently decoding, a real, measurable "generation stall." Chunked prefill (Agrawal et al., Sarathi and Sarathi-Serve) fixes this by splitting a long prefill into fixed-size chunks and interleaving one chunk per iteration alongside ongoing decodes, bounding the latency hit any single iteration can take. It's now the default scheduling strategy in vLLM and SGLang, and it's the answer if asked how a scheduler actually decides what goes into a given batch.

PagedAttention (Kwon et al., 2023, the vLLM paper) is worth stating in its own terms rather than as a loose metaphor, because the authors built it as a literal application of OS virtual memory: block as page, token as byte, request as process. Divide each sequence's KV cache into fixed-size blocks (16 tokens' worth of K,V is a common choice). Store blocks anywhere in a shared pool of physical GPU memory, not necessarily contiguously. Give each sequence a block table mapping its logical block index (0, 1, 2, in generation order) to a physical block index in the pool, exactly a page table mapping virtual pages to physical frames. The attention kernel itself has to change to match: instead of assuming a flat, contiguous KV buffer, it walks each sequence's block table and gathers K,V from wherever the blocks actually live, an indirect, gathered access pattern rather than a simple contiguous read.

The benefits follow directly from the mechanism. Internal fragmentation is bounded by `block_size - 1` tokens per sequence (at most 15 wasted tokens with 16-token blocks, versus potentially thousands wasted under a naive max-length reservation). External fragmentation disappears since every block is the same size and interchangeable. And sequences sharing an identical prefix, a common system prompt, or parallel-sampling and beam-search branches off the same prompt, can point their block tables at the **same** physical blocks, with a copy-on-write triggered only when a sequence actually needs to diverge, exactly `fork()`'s copy-on-write page semantics. Reported throughput gains from PagedAttention plus continuous batching together run 2 to 4x over prior serving systems, and the gain grows with longer sequences, larger models, and more complex decoding where prefix sharing pays off most.

The honest caveat: gathering from non-contiguous blocks is not free at the kernel level. Indirect addressing is a less predictable access pattern than a flat contiguous read, costing some raw kernel efficiency relative to the naive layout. The memory-efficiency and prefix-sharing wins dominate in essentially every real serving workload, which is why almost every serving engine has adopted paging, but it's worth knowing the tradeoff exists rather than treating it as costless.

## 8. Quantization

The core operation, symmetric linear quantization: for a tensor W, pick a scale `s` and compute `W ≈ s · round(clip(W/s, -127, 127))`, storing the int8 values plus `s`. Dequantize by multiplying back.

Two different things get lumped under "quantization" and they pay off at different phases of inference, which matters because of the memory-bound-decode fact from section 6. **Weight-only** quantization (weights in int8 or int4, activations stay fp16, dequantized on the fly at or fused into the matmul) doesn't speed up the matmul itself, since the arithmetic still runs at higher precision. What it does is cut the bytes streamed from HBM to load the weights, and since decode is bottlenecked precisely on bytes moved, weight-only quantization speeds up decode roughly in proportion to the bytes saved, even though not a single FLOP got faster. **Full W8A8** (weights and activations both quantized, the matmul actually executed in int8) needs activations quantized on the fly too, since their ranges are input-dependent, either via a calibration pass fixing static ranges or dynamic per-token quantization at runtime. This genuinely speeds up the matmul, exactly 2x the FLOPs/s of fp16 tensor cores on the same A100 silicon (624 int8 TOPS versus 312 fp16 TFLOPS), which matters most for the compute-bound prefill phase, where you weren't memory-bound to begin with and raw throughput is the actual constraint.

Granularity: per-tensor (one scale for the whole matrix, simplest, least accurate), per-channel or per-row (one scale per output channel, the common default for weight quantization), per-group (one scale per, say, 128 weights along a row, used when per-channel still isn't accurate enough).

The complication specific to transformers is worth naming precisely: LLM.int8() (Dettmers et al., NeurIPS 2022) documented that a small number of feature dimensions, consistently the **same** dimensions across nearly every token, carry systematically larger magnitude than the rest, in every billion-parameter-plus model the authors examined. These outliers make up roughly 0.1% of feature dimensions but wreck a naive uniform quantization range if forced into the same 256-level int8 grid as the other 99.9%. The fix is mixed-precision decomposition: identify outlier dimensions (magnitude above a threshold, α = 6.0 in the original paper), compute those in fp16 via ordinary matmul, compute everything else in int8, and sum the two partial results. Worth stating plainly since it cuts against the obvious expectation: this decomposition preserves accuracy well, but the irregular, scattered fp16 computation it requires adds real latency overhead, in some cases enough to be slower than plain fp16 inference. That's exactly why later work like SmoothQuant took a different approach, mathematically migrating the outlier difficulty from activations into the weights ahead of time via a per-channel scaling transform, so the runtime matmul stays uniformly int8 with no decomposition needed at all. Production high-throughput W8A8 systems tend to look more like SmoothQuant than like literal LLM.int8() for exactly this reason.

## 9. nsys vs ncu, and the roofline model

nsys (Nsight Systems) is a system-wide timeline across CPU and GPU: kernel launches, H2D/D2H memory copies, CPU-side CUDA API calls, and, if you instrument with NVTX ranges, your own logical phases. What it's uniquely good at is showing the **gaps** between GPU work, your signal for whether you're actually GPU-bound or secretly stalling on CPU-side launch overhead, framework overhead, or an unnecessary sync point. It's the first tool to reach for whenever end-to-end wall-clock doesn't match what per-kernel microbenchmarks would predict, and small-batch decode is exactly that regime: many small kernel launches per step, where launch overhead can dominate actual kernel execution time if you're not fusing aggressively or capturing a CUDA graph.

ncu (Nsight Compute) is the deep, single-kernel profiler (section 3 covers what it reports and how to read the stall reasons). The short version of the division of labor: nsys tells you which kernel or gap is the problem across the whole run; ncu tells you why that specific kernel is slow.

Roofline model: plot achieved performance (FLOPs/sec) against arithmetic intensity (FLOPs per byte of HBM traffic) for a kernel. Two bounding lines: a sloped one, `performance = arithmetic_intensity × peak_HBM_bandwidth` (you're bandwidth-limited, can't outrun the rate memory delivers data), and a flat one at the device's peak FLOPs/sec (you're compute-limited, memory can keep up but the tensor cores are maxed). Achieved performance sits at the minimum of the two. The **ridge point**, where the lines cross, is `peak_FLOPs / peak_bandwidth`, and where a kernel's arithmetic intensity sits relative to it tells you immediately which kind of optimization is even possible: below the ridge, you need to cut bytes moved (fusion, better tiling, lower precision); above it, you need to cut or better-schedule FLOPs.

Two concrete ridge points worth having memorized. A100 SXM: 312 TFLOPS fp16 tensor-core (dense), roughly 2 TB/s HBM2e bandwidth, ridge point around 155 to 160 FLOPs/byte. H100 SXM: roughly 1000 TFLOPS fp16 tensor-core dense, roughly 3.35 TB/s HBM3e bandwidth, ridge point around 300 FLOPs/byte. Compute grew faster than bandwidth across that generation, which means a kernel that was comfortably compute-bound on A100 at a given arithmetic intensity can be bandwidth-bound on H100 at that exact same intensity: worth remembering before comparing benchmark numbers across the two devices at face value.

This is precisely why naive attention is memory-bound despite looking FLOP-heavy on paper: accounting for the repeated N² HBM round trips, its actual arithmetic intensity sits well below the ridge point. FlashAttention's entire value proposition is moving that same computation's effective arithmetic intensity up past the ridge by cutting HBM traffic, not by cutting FLOPs. FA2 does the same total matmul FLOPs as naive attention; it just uses far fewer bytes to do it. That is what "IO-aware, not approximate" cashes out to on a roofline plot.

## 10. ZeRO and ring all-reduce (stretch)

ZeRO has three stages, each partitioning more of the optimizer state across data-parallel ranks than the last: stage 1 shards optimizer states, stage 2 additionally shards gradients, stage 3 additionally shards the parameters themselves. Stages 1 and 2 keep the **same** communication volume as standard data parallelism (one gradient all-reduce per step) while cutting memory substantially, close to a free lunch, which is why they're close to a default choice whenever memory allows. Stage 3 is the real tradeoff: since no rank holds a full parameter copy, every forward and backward pass needs an on-the-fly all-gather of whichever parameter shard is about to be used, layer by layer, a substantial extra communication cost paid continuously through the step rather than once at the end. Reach for stage 3 when the model genuinely doesn't fit in stage 1 or 2's memory footprint, not by default.

Ring all-reduce, the mechanism under standard multi-GPU data parallelism: with N GPUs, split the gradient buffer into N equal chunks. Two phases, each N-1 steps. A reduce-scatter phase: at each step every GPU sends one chunk to its ring neighbor and receives-and-sums a different chunk from its other neighbor, so that after N-1 steps every GPU holds one fully-reduced chunk, a different one per GPU. Then an all-gather phase, another N-1 steps, circulating those fully-reduced chunks around the ring until every GPU holds the complete result. Total: 2(N-1) steps, and each GPU sends and receives roughly `2(N-1)/N` of the buffer's size, which approaches a constant (about twice the buffer size) as N grows, independent of how many GPUs you add. That's what "bandwidth-optimal" means precisely: no algorithm can move less data per GPU and still deliver the fully-reduced result to everyone, since each GPU needs to touch at least the `(N-1)/N` fraction of the buffer it didn't originally hold, and ring achieves that lower bound exactly.

Bandwidth-optimal is not the same as latency-optimal, and this is worth stating plainly rather than glossing over: the 2(N-1) step count is linear in N, so at large N the fixed per-step latency, not the bytes moved, starts to dominate wall-clock. That's why hyperscale training clusters and modern NCCL increasingly blend ring with tree-based or hierarchical approaches (double binary trees, which trade a little bandwidth-optimality for logarithmic-in-N latency) once N is large enough that step count itself becomes the bottleneck. For a single-node multi-GPU retrofit, plain ring all-reduce is the right call outright; the caveat matters if asked to reason about scaling to dozens or hundreds of nodes.

## 11. Applying the HFT playbook to LLM serving

The primitives here (lock-free SPSC/MPSC rings, memory ordering, thread pinning, cache-aware layout) need no re-explanation. What's specific to LLM serving is where they get applied and what changes about the workload.

**Coordinated omission**, precisely, since it's a specific, nameable measurement error rather than a vague "be careful" warning: if a load generator doesn't issue requests on a fixed, independent schedule, then when the system stalls, a GC pause, a queue backup, a slow decode step, the requests that **would** have arrived during that stall, and would have queued behind it experiencing the worst latency of anyone, never get sent at all, so they never appear in the measured latency distribution. Your p99 looks fine because the actual worst-case requests were silently omitted from the sample. The fix is an open-loop generator that issues requests on a fixed schedule (Poisson arrivals at a target rate, typically) regardless of how the system is responding, so a stall shows up honestly as a cluster of high-latency or timed-out requests, the way real production traffic would actually experience it.

**Per-stage latency decomposition** for this specific pipeline, the direct analogue of tracing a market-data event through parse, normalize, strategy, and order-out: enqueue (request lands on the ingress queue), schedule (admitted into the running batch), prefill (first-token compute, for requests without a cache hit), per-decode-step time (usually reported as inter-token latency, and the number that degrades as effective batch size grows), detokenize, response write. Instrument each boundary. When p99 is bad, this tells you which stage owns the tail instead of leaving you to guess, exactly like isolating whether a slow trade was slow at the exchange, the parser, or the strategy itself.

**Why the threading model matters here specifically:** IO thread(s), scheduler thread, GPU worker thread(s), connected by lock-free rings rather than mutex-guarded queues, for the same reason as any latency-sensitive pipeline: avoiding OS-scheduler-mediated wakeup latency and priority-inversion risk on the hot path. The one genuinely LLM-serving-specific wrinkle, versus a typical market-data pipeline, is that the GPU worker's per-iteration processing time isn't fixed. It depends on the current batch composition, how many sequences, whether any are mid-prefill, so the scheduler is making an admission decision against a variable-latency downstream stage rather than a roughly-constant one. That variability is exactly the problem chunked prefill (section 7) exists to bound.
